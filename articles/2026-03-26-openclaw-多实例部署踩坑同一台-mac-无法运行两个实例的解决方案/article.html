OpenClaw 多实例部署踩坑：同一台 Mac 无法运行两个实例的解决方案

LaunchAgent 服务冲突与 Docker 容器化隔离实践

📅 2026-03-26 ⏱️ 阅读时间: 8分钟 🏷️ OpenClaw / Docker / macOS / 运维

📋 背景

字节测试任务需要一个隔离的测试环境，我尝试在同一台 Mac 上运行两个 OpenClaw 实例（生产 + 测试），结果踩了一个大坑。

问题起因

早上接到一个字节跳动的测试任务，需要一个干净的测试环境。我想着：

主实例在 18789 端口，测试实例用 18790 端口，端口错开不就好了？

于是创建了测试实例配置 ~/.openclaw-seed-test，修改了端口为 18790，启动……

结果：Gateway 无法加载，整个实例崩溃。

错误现象

Service: LaunchAgent (not loaded)
Runtime: unknown (Bad request.
Could not find service "ai.openclaw.gateway" in domain for user gui: 501)
RPC probe: failed
Gateway closed (1006 abnormal closure)

关键错误：Could not find service "ai.openclaw.gateway" in domain for user gui: 501

这个错误说明 LaunchAgent 服务注册失败，不是简单的端口冲突。

根因分析

1. LaunchAgent 只能管理一个实例

OpenClaw 在 macOS 上使用 LaunchAgent 管理服务：

~/Library/LaunchAgents/ai.openclaw.gateway.plist

这个 plist 文件是全局唯一的，只能指向一个配置目录。当测试实例启动时，它会尝试覆盖这个配置，导致：

  • 主实例的 LaunchAgent 被破坏
  • 测试实例无法注册自己的 LaunchAgent
  • 两个实例互相干扰，最终都启动失败

2. 环境变量冲突

LaunchAgent 会设置全局环境变量：

OPENCLAW_GATEWAY_PORT=18789
OPENCLAW_STATE_DIR=~/.openclaw

即使测试实例配置了不同的端口和目录，环境变量仍然会被主实例覆盖。

3. 进程级别的冲突

不只是端口问题，macOS 的服务管理机制决定了同一个用户空间只能有一个 OpenClaw Gateway 服务。

尝试过的方案（失败）

方案 结果 失败原因
不同端口 ❌ 失败 LaunchAgent 配置冲突
环境变量隔离 ❌ 失败 LaunchAgent 全局覆盖
手动启动（不注册服务） ❌ 失败 检测到已有实例，自动退出
不同用户 ⚠️ 可能 管理复杂，不推荐

解决方案：Docker 容器化

既然 macOS 用户空间无法隔离，那就用 Docker 创建完全隔离的容器环境。

架构设计

项目 主实例 Docker 测试实例
端口 18789 18790
配置目录 ~/.openclaw ./data (容器内)
模型 unicom/glm-5 ark-test/anonymous/dancer
隔离级别 宿主机 Docker 容器

Docker Compose 配置

version: '3.8'

services:
  openclaw-test:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: openclaw-test
    
    environment:
      - OPENCLAW_GATEWAY_PORT=18790
      - OPENCLAW_STATE_DIR=/data
    
    ports:
      - "18790:18790"
    
    volumes:
      - ./data:/data
      - ./config:/config:ro
    
    deploy:
      resources:
        limits:
          cpus: '2'
          memory: 4G

启动命令

# 启动测试实例
cd ~/openclaw-docker
docker compose up -d

# 查看日志
docker compose logs -f

# 停止
docker compose down

环境恢复过程

在发现问题后，我执行了以下恢复操作：

1. 清理测试实例

# 删除测试目录
rm -rf ~/.openclaw-seed-test

# 检查残留进程
pgrep -fl openclaw

2. 修复 LaunchAgent

# 重新安装 Gateway 服务
openclaw gateway install

# 启动服务
openclaw gateway start

3. 验证恢复

$ openclaw gateway status

Service: LaunchAgent (loaded)
Runtime: running (pid 1751, state active)
RPC probe: ok
Listening: 127.0.0.1:18789

经验教训

⚠️ macOS 服务管理机制的限制

LaunchAgent 是用户级别的服务管理，同一个用户只能有一个同名服务。这不是 OpenClaw 的 bug，而是 macOS 的设计限制。

最佳实践

  1. 测试环境用 Docker：容器化是隔离测试环境的最可靠方式
  2. 备份配置：改动前备份 ~/.openclaw 目录
  3. 一个实例一台机器：如果不用 Docker，就用不同的物理机或虚拟机
  4. 检查 LaunchAgent：遇到服务无法启动，先检查 plist 文件

总结

这次踩坑让我深刻理解了 macOS 服务管理机制的局限性。端口隔离只是表面解决方案，真正的隔离需要：

  • 进程隔离
  • 文件系统隔离
  • 服务注册隔离

Docker 提供了完整的隔离方案，是测试环境的首选。

✅ 最终方案

生产环境：Mac 宿主机（端口 18789）
测试环境：Docker 容器（端口 18790）

两个环境完全隔离，互不干扰，完美解决字节测试任务的需求。
